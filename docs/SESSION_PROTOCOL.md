# Stateful exploration contract

## Initialize and resume

Resolve a session directory outside the library checkout, such as a sibling `naming-sessions/<session-id>/`. Separate users and brands. Copy templates only for a new session; never overwrite existing records. Once files are written, give the user a clickable link or resolved path to the shortlist. Without write tools, keep equivalent state in chat and offer portable Markdown.

On resume, read both records, summarize the active branch and latest decision, and continue from recorded preferences. Missing state is unknown, not permission to invent previous decisions. Ask one focused question if contradictory feedback affects the next action.

For review evidence, distinguish a same-agent read-back from a fresh-context resume. A fresh reader receives only library instructions and the two current session files, without the executor's transcript, future scenario or expected answers. Record the actual input boundary and reader output outside the library; a disk read by an already informed agent does not demonstrate context isolation.

## Onboarding method overview

In the first response of a new naming exploration, show **every active generation method** from the [operational catalog](METHOD_CATALOG.md#operator-and-neighbor-audit), currently eighteen. Render the overview directly in the conversation, in the user's language: a readable name for each method plus one short explanation of what it does, grouped by family or in a compact table. The operator table is the source of the full set; do not substitute only recommended methods, a link, a collapsed section or “and others”. Exclude archived methods, deprecated routers and lexical universes. Present screening separately as a later check, not a nineteenth generation method. Label the methods collectively as draft procedures available to try, not individually accepted methods.

Say explicitly: “You can ask for any method by name, combine methods, or leave the choice to me. You do not need to choose one to start.” For example: “Use metaphor mining”, “Try etymology”, or “Combine clipping and respelling”, translated naturally. Showing the catalog does not authorize running all methods or require loading all eighteen skill files.

Continue in the same response: with a sufficient brief, offer useful contrasting directions under the ordinary start rule; otherwise ask the most useful brief question. Record `onboarding_methods_shown` with the displayed method IDs and response turn in the exploration log, or equivalent in-chat state. On resume, reuse that record instead of repeating the full overview. Show it again on request; if older state lacks it, provide the overview once when creative exploration resumes. A standalone screening request follows screening intake, not a forced creative onboarding.

## States and transitions

| State | Action | Exit condition |
|---|---|---|
| BRIEF | Establish offer, audience, character, exclusions; ask only questions affecting direction | Enough information for contrasting previews; mark assumptions |
| METHOD_MENU (optional navigation) | All methods are shown once at onboarding; later explain selected methods in depth or redisplay all on request | User can request any named method without choosing one to start |
| UNIVERSE_MENU (optional) | Ordinarily infer two distant worlds; expand to 6–12 on request or useful uncertainty | Develop a provisional branch or user choice |
| DEEP_EXPLORE | Follow the skill, preserve sources, generate diverse clusters | Useful batch or research dead end |
| REFINE / NAVIGATE | Deepen, switch, combine, revisit, shortlist, review research, or stop | User selects next action |
| SCREEN | Run preliminary screening for selected names/scope on request or before final recommendation | Dated bounded report, including any incomplete/unperformed checks |
| EXPORT | Return only explicitly saved names with origins, notes and preliminary status/scope | User stops or returns to exploration |

States are navigation aids, not compulsory gates. A sufficiently specified ordinary brief can move directly from BRIEF to useful exploration: state concise assumptions, show 2–3 contrasting directions/names and recommend one. This is an agent provisional choice, not invented user delegation. Preserve other possibilities for later navigation. Honor direct instructions from any state without requiring repeated confirmation. Menus invite creative choices; they are not permission checks for every research step. If the user delegates direction selection, record the provisional choice and proceed. Never auto-complete because a batch or count is reached.

## Conversation and customer languages

Record `conversation_language` for the dialogue and report narrative, `customer_language` for customer-facing copy, and `language_basis` (received user turn or explicitly provisional assumption) in both session files. Resolve customer language from the audience/market brief, not the language of the chat or the name's script. For a mixed international audience, English can be a stated provisional common language; invite correction without blocking a useful preview. When plausible language choices would materially change the examples and the brief does not resolve them, ask one short question. On resume, preserve the recorded choice; missing fields in older records are unknown, not a reason to overwrite the session.

Use `customer_language` for the shared `category_descriptor`, package text, customer messages and materials proposed for audience testing. Keep the same descriptor and sentence frame across names. Explain the comparison in `conversation_language`. Preserve these choices in expanded brief snapshots and worker inputs. In the final document, state the intended customer language and retain customer-facing examples in that language, even when the surrounding report is in the conversation language. Label local-language drafts requiring native-speaker review, including Serbian; proposed translations are not validated local copy. Exact user quotes stay in their original language.

## Branch and candidate identity

Use stable branch IDs (`B01`) and candidate IDs (`B01-C01`). Each branch records parent, method, universe, status, source references, feedback, and next opportunities. Park rather than erase branches when switching. On revisiting, recover sources and preferences. Hybrid branches name component methods and their execution order. Do not duplicate a candidate merely because it appears on multiple branches.

Separate candidate **form** (`attested`, `adapted`, `invented`) from **evidence** (`verified`, `unverified`, `not applicable`). A verified source word does not make its adapted candidate attested. Each research-derived candidate records the exact source term, source ID, supported meaning, and transformation. Sound inventions have no fabricated etymology.

## Persistence and consent

Update the exploration log after meaningful research, feedback, branching, or selection. Keep it compact but preserve enough references to recover parked paths. Detailed evidence may live in a session-owned `RESEARCH_NOTES.md`, outside the library.

Save only explicitly selected candidates to the shortlist. Praise alone is not a save instruction. Clarify ambiguous selections. Preserve exact spelling and user comments. Removal and substantive replacement require user approval. Repeated selection updates an existing entry rather than duplicating it. Around 20–25 entries offer voluntary review without blocking additions.

Export includes name, method, universe (or not applicable), origin, form, lexical evidence, source references and user comments when available, plus the preliminary screening status/date/scope/report link beside each name. Keep unresolved claims and unperformed checks labeled; no status is legal clearance. Never claim a file was saved unless the write succeeded.

## Preliminary screening and tenant scope

The [name-screening skill](../checks/name-screening/SKILL.md) is a review stage outside the eighteen-method catalog. It can be entered from any state on request and is required before a final recommendation. Ordinary creative previews may be unchecked and labeled; a final creative working choice or directly requested unchecked export must explicitly retain incomplete/unperformed checks and cannot be presented as ready for launch. Preserve user control and explicit shortlist consent.

Record `active_tenant_profile` as path/revision/selection turn, or none. Load only the explicitly selected profile and its decision history; do not scan for other tenants. A stricter selected profile can require registry-before-preview/acceptance and local document-change conventions. These are not global defaults. No default territories, Nice classes, reference names or sound filters are inherited.

Keep session-owned check reports using [NAME_CHECK.md](../templates/NAME_CHECK.md); `name_checks` maps candidate IDs to check ID, scope revision, selected boundary, decision status, coverage, date and report path under the [boundary policy](../checks/name-screening/RISK_BOUNDARY.md). Ask for an explicit boundary choice at screening intake unless already recorded; ordinary creative assumptions do not authorize this choice. Search keys never replace the exact display name. Changing the name, goods/services, territory, language, risk boundary/constraints or material profile rule marks the old conclusion stale for the new scope; preserve the old report, create a revision and state required rechecks. Decision records keep date, reason, source, decision type and any new argument or correction. Do not re-propose a rejected variant without a new argument or explicit request, and do not remove a favorite automatically because a check raises a concern.


## Concrete evidence and reconciliation rules

Screening uses the [registry recipes](../checks/name-screening/REGISTRY_RECIPES.md) and [coverage ledger](../checks/name-screening/COVERAGE.md). Store the ledger beside the report, record automated/manual validation and put one recommended next action beside a material finding. A repeat run receives a new check ID; unchanged scope can keep its revision, but inherited evidence retains its original observation date.

`verified` applies to an ingredient/sense actually inspected, not to effectiveness, availability or the complete invented string. A supplied ordinary-English fixture ingredient may use `not applicable` when no external research claim is made. Mixed-source candidates list evidence per source; any unresolved asserted meaning makes overall lineage evidence `unverified`. Source IDs are scoped to a session; bibliography IDs must be explicitly labeled as such.

When switching, write the former branch as parked and create a child (derivation) or sibling (new direction). Preserve IDs across revisits. An unchanged candidate reused in a new branch keeps its original candidate ID and gains a branch reference. Reconcile favorites in both files after each consent event; if only one file was written, record the incomplete write and repair before claiming persistence. Never copy templates over a resumed session.

No write tools: retain equivalent state in chat; normally show a compact summary and state that no file was saved. Provide complete portable “state” and “shortlist” fields on request or handoff, rather than repeating every field each turn. On a failed write preserve the last confirmed state and provide exportable text. A resume summary names exact favorites, active branch, parked opportunities, rejected directions and the latest actual instruction; unknown prior feedback stays unknown.

## Received-evidence boundary (internal memory and audit)

Assign received user turns stable IDs (`T01`, `T02`, …), including synthetic turns. Record `received_through` in both session files and cite the originating received turn for decisions, delegation scope, rejection and shortlist consent/comments. These are internal references, not extra questions or forms for the naming user. Agent hypotheses, provisional choices and pending questions stay explicitly labeled; they are not user preferences.

Keep exact quotes in their original language and spelling. Put translations or summaries in a separate labeled field; never present them as exact comments. Repeated selection retains the candidate ID and the prior consent/comment history with its turn IDs.

In sequential trials, the executor and any writing helper may access only the received transcript prefix. Do not read future fixture turns, expected preferences, expected comments or answer keys, even when available on disk. The trial controller supplies one turn at a time and keeps future material outside the executor's accessible context; an instruction alone is not evidence that this boundary held.

After each meaningful write, reconcile both files against that received prefix: latest decision, delegated choices, rejected directions, favorites and exact comments. Check that every asserted user fact cites a received turn and no field anticipates a later instruction. Normal session files evolve forward. For audited trials, retain immutable copies of both records at each meaningful write, labeled by received-through turn and write sequence. Append a correction event and create a later snapshot if repair is needed; never replace failed historical checkpoints or retroactively validate them using later feedback. Record final-state reconciliation and historical consistency separately.

For internal reconciliation and requested audit reports, use unique candidate IDs as the counting unit. Report `total records = conforming candidates + out-of-operator diagnostics`; divide conforming candidates into retained, parked and rejected for the current brief (`conforming = retained + parked + rejected`). A parked conforming candidate remains counted and recoverable. Label the assessment layer (worker or conductor); do not combine their counts or overwrite earlier judgments. A mechanically valid but rejected candidate remains conforming; an invalid construction remains a diagnostic even if discussed. Shortlisted count is a separate subset of conforming candidates, not an additional total. Keep branch references from double-counting reused IDs and state any other counting unit explicitly.

## Ordinary presentation and internal work

Keep stable IDs, source status, exact maps, consent turns and compact reconciliation internally. Normally show only 2–3 meaningful contrasts, why each fits, a concrete drawback and a proposed reading where needed. Say “invented,” “adapted from a checked sense,” or “unverified lead” tersely; never hide a material uncertainty for brevity. Full ledgers, typed graphs, corpus arithmetic and detailed maps are available when requested or necessary to explain a material limit. All skill grids and batch sizes are private defaults; useful smaller batches are valid. Audit checkpoints, immutable snapshots, hash checks and full historical reconciliation are trial/maintenance work only, never ordinary naming-session gates or user-facing forms. Portable memory and explicit shortlist consent still apply.

## Research framing and contextual comparison

For an expanded search, freeze a concise brief: audience, problem, credible promise, difference from alternatives, voice, pronunciation target, unwanted associations, target countries, conversation/customer languages and their basis, and assumptions. Keep a plain category descriptor (usually 2–4 words) in the customer language separate from the name. Infer missing nonessential fields explicitly; ask only when the answer changes direction.

When differentiation matters, inspect a small dated sample of competitor names on their own sites. Record URLs, recurring structures, imagery and tone, then propose departures as hypotheses. This is a creative namescape, not a conflict or availability search; a small sample cannot establish market-wide uniqueness. Reuse the map across methods.

Compare promising names in the same plain introduction, descriptor and realistic use context. Separate name fit, message comprehension and personal liking. Record actual feedback separately from predicted reactions. If real participants are available, ask what they think the offer is, how they would pronounce/write the name, and which associations it evokes; do not substitute simulated respondents. Before final selection, recommend native-speaker review in relevant countries for pronunciation, slang and cultural associations. The screening stage records preliminary evidence and gaps; legal approval and registration remain outside this workflow. See [research basis](research/PROCESS_RESEARCH.md).

## Form before story

For each proposed representative, record three ordered editorial passes: (1) exact name alone, plausible readings/stress, likely spelling uncertainty and obvious unwanted associations; (2) the same customer-language descriptor and use sentence for every name, assessing brief fit; (3) verified origin and metaphor, including explanation burden. Freeze the first two observations before adding the story. With file tools, save a separate form/context checkpoint before writing the origin assessment; later corrections must remain separate. Without file tools, emit the form/context record before the story and keep the boundary explicit. If this order was not recorded, label it not demonstrated; a later reordered report does not retroactively prove it. Do not let an appealing origin override a failed hard brief constraint. Separate hard filters from soft preferences and provisional agent assumptions; an ambiguous reading is a risk, not automatically a failure unless the brief makes it so.

These are agent predictions, not listener tests. The generating agent already knows the source: ordering alone is not a blind evaluation. Claim a blind read only when a fresh evaluator actually receives names without their origins; record that input boundary. Actual audience feedback remains separately attributed. The concise user-facing comparison may combine the observations after these passes.

## One bounded adaptation pass

When research yields a useful, supported image but weak direct names, preserve the source branch and attempt one bounded child pass if refinement is within the user's request. Choose at most two initial source anchors/branches and diagnose each defect before selecting an operator using the table below. Read the chosen method; generate at most three variants per anchor. A replacement source or independent sound branch spends the same branch budget, rather than adding unlimited work. These limits override larger method batch defaults for this pass. Before generating variants, record the specific defect to improve, parent candidate/source IDs and unchanged brief constraints. Record each resulting variant’s exact edits and form/evidence after generation. Also freeze whether source recognition is required or optional, citing the user brief or a provisional agent assumption. Do not infer a user preference or relax this target after seeing the variants. A shorter name that loses required recognition is not an improvement; where recognition is optional, record the loss as a tradeoff. An unchanged source is a comparison control, not a new constructed candidate.

Evaluate the entire generated bounded batch against its anchors using form, shared product context, then story; a failed variant does not skip the remaining variants. Retain a variant as a local lead only if it improves the named defect without introducing a harder failure; park the others. After evaluating the batch, close the adaptation pass regardless of how many leads remain. Zero improvements is a valid result. Do not recursively repair the repairs or restart all methods; offer one different source/sound direction for subsequent exploration. Preserve the supported source property as a metaphor, not a claim that a shortened or invented string retains the dictionary meaning. Unsupported meaning is a research gap, not something spelling can repair.

An adaptation never clears an existing market or registry concern. Carry that concern forward as unresolved context and require a new scope-specific check for the new spelling; do not copy the parent's clearance status. If a useful sound cannot be preserved by the selected operator, stop or record a separately authorized future branch rather than silently changing methods.

### Choose the next operation by defect

| Observed defect | Bounded next operation | Stop or avoid |
|---|---|---|
| Excess length; a useful recognizable segment survives | clipping | Do not shorten merely because it is easy; reject cuts that fail the frozen recognition target |
| Spoken form fits; spelling creates friction | respelling, preserving target sound | A sound change belongs to phonetic-invention, not hidden respelling |
| Source image fits; the word itself is awkward | replace the anchor with another object, action or outcome from the same verified property family using lexical-research | Record the retired anchor, new source and reason; only one replacement in this pass, occupying the same branch and research budget; count its selectable name in the candidate cap, no replacement chain |
| Desired sound character matters; lexical origin adds little | an independent phonetic-invention branch | No invented etymology; do not claim a sound-only control derives from the rejected anchor |
| Material close-market concern under the selected occupancy boundary (ask if unknown) | use a different source or sound direction | Cosmetic edits do not resolve the concern; keep it recorded and screen new candidates separately |
| No material defect or useful operator | keep the direct word or park the branch | No obligation to adapt, fill slots or contribute a winner |

Choose by the defect, not a quota of different operators. Record the reason before constructing names. Do not default every world to clipping; choosing the same operator is valid when independently justified. Replacement and sound routes are alternative uses of the bounded pass, not extra rounds. Source-recognition requirements may rule out sound invention; do not silently relax them to obtain a result.

### Independent sound control

When a research-derived adaptation loses most recognizable source meaning and the source target permits that loss, compare its form against up to two independent sound-first controls under the same brief and constraints. Use phonetic-invention, with no semantic roots, and one control branch per run rather than per candidate. This two-control limit explicitly overrides that child method’s larger default spoken-form and spelling grids; do not secretly generate a larger pool and report only two survivors. Reuse a suitable existing sound-first branch when present. Controls consume the declared candidate budget: reserve slots before generation or reduce the adaptation batch; never silently enlarge a comparison arm. A separately budgeted follow-up must be labeled as such. If scope or budget prevents the control, record it unperformed and limit any claim that research improved the name.

Present candidate and controls without origins using the same contexts. Record which quality, if any, justifies preferring the researched form. No advantage is a valid outcome; an expensive source trail is not a quality bonus. Keep the original lineage and form/evidence even when the sound control wins. Agent comparisons are hypotheses, not consumer measurements.

## Compare against a standing alternative

Before promoting a new working lead, compare it with one or two earlier suitable working leads in the same name-only and product-context frames. Record what improves, what worsens and what observation could change the preference. Existing leads are controls, not automatically user favorites. Use actual session records; if no prior lead exists, state that and compare current alternatives. Preserve prior judgments and later corrections; do not treat the newest batch winner as the overall winner by default. Ties and no improvement are valid. A candidate with a known serious concern may remain a labeled creative benchmark, but not an unqualified development recommendation.

Before saying a candidate is worth further development, perform the [bounded market look](../checks/name-screening/SKILL.md#bounded-market-look-before-development) for the proposed development leads (up to three; one is sufficient). Form and contextual comparisons remain separate from market evidence; do not alter the creative verdict merely to hide a concern. This is not a new requirement to screen every generated name or a substitute for scoped final screening.

## Parallel exploration: three or all eighteen

Offer once when the brief supports exploration, alongside useful initial contrasts. Use outcome-based choices in the conversation language: **three different directions** for a focused comparison, or **a broad search** for more varied possibilities that takes longer and uses more work. Recommend the focused option when appropriate; continuing the current direction is also available. For example: “I suggest comparing three different directions next. We can also explore more broadly; that takes longer and does not guarantee a stronger name. Or we can develop the direction you already like.” The user chooses the result, without needing to select professional method names or understand subagents. Technical detail is available on request. Do not repeat the choice or require it before a useful preview.

Internally, the focused choice maps to three distinct suitable methods, and broad search maps to all 18 active methods, one dedicated subagent per method. Preserve explicit requests for named methods or worker arrangements. An explicit selection of either plain-language option authorizes its mapped run; no second confirmation is needed. All current methods remain draft trials. Follow the existing coverage and fallback rules below.

Check the actual available worker tools rather than assuming a client supports delegation. When none are available (for example, stock Pi), offer the same comparison **one direction at a time in this chat**, explicitly as sequential work, before the user selects it. That selection authorizes the sequential run with the same method coverage ledger; record the conductor as executor instead of fictitious worker IDs. If the user explicitly requested separate workers, obtain their choice before substituting sequential work. Ordinary single-direction exploration remains available without worker tools. Research access is a separate capability; unavailable source evidence stays unverified.

### Assignment axis

Record `axis: methods | universes` and execution separately (`parallel | queued | sequential`). Default focused/broad choices retain the three/all-eighteen method mapping above. An explicit request to deepen selected source worlds uses `axis: universes`: one dedicated worker per named world with the same selected method (normally lexical-research). This is not a three-method run or an all-method sweep. Do not substitute different methods for the selected worlds. Universe cards are parameters, not new methods.

For either axis freeze assignments before dispatch: `assignment_id`, `method_id`, `universe_id` (or not applicable), run ID and brief revision. Use assignment IDs, not method IDs alone, for identity, coverage and retry: repeated method IDs are expected in universe runs. Every worker must echo the full tuple; a wrong or missing assignment/universe remains unresolved even if run and method match. Apply the worker, reconciliation, no-yield, fallback and presentation rules below to both axes; references to expected methods mean expected assignments for universe runs. Child adaptation methods do not satisfy additional assignments. The legacy three/all-method modes remain unchanged apart from explicit assignment identity.

1. **Plan.** Read the active catalog. Freeze a run ID, brief revision, received-through turn, selected method IDs and common comparison contexts. For three, prefer different families and explain fit. For all, assign every active method exactly once (currently 18); exclude deprecated routers and archived entries. Record the expected set before dispatch.
2. **Dispatch.** Create one dedicated subagent per assignment (method or selected universe); record the host-returned worker reference against that assignment. Give each the same brief snapshot, its method file, source contract, shared namescape if any, relevant evidence files and any explicitly required child method. A child operation does not count as completing another assignment. Workers may infer method-specific parameters but must label them. Queue dedicated workers when concurrency is limited; do not give several assignments to one worker and call that one-subagent-per-method. If the host lacks subagents, explain this and offer sequential exploration of the same selected method set with the same coverage ledger and reconciliation. Obtain the user's choice before substituting it for an explicitly requested subagent run; never claim parallel execution occurred.
3. **Worker contract.** Return assignment ID, universe ID, run ID, method ID, brief revision, status (completed/no-yield/blocked/failed), method-specific intermediate artifact, candidates with local IDs, exact transformations, source records, form/evidence, proposed pronunciation, fit and drawback. No-yield is valid when the method does not fit; do not manufacture candidates or source evidence. Workers must not edit shared session files, select favorites, impersonate users or launch nested workers. They may read referenced child instructions without extra delegation.
4. **Reconcile.** The conductor is the sole writer of shared state. Validate the returned assignment ID, universe ID, run ID, method ID and brief revision against the assignment before accepting its status or candidates. Reject mismatched envelopes as unresolved assignments; do not infer identity from a filename alone. Validate each result against its assigned operator and brief revision; keep nonconforming outputs as diagnostics. Map local source/candidate IDs into session IDs. Exact repeated spellings share one candidate ID and retain every branch and lineage; conflicting provenance stays explicit rather than upgrading evidence. Keep spelling variants separate. Preserve alternative lineages separately through shortlist export, including their distinct form/evidence fields. When the brief changes, cancel pending old work where possible or mark it stale; park old results. Start a new revision with its own expected set. Coverage is scoped to run ID plus brief revision: old results never satisfy new assignments.
5. **Check coverage.** Compare validated returned assignment IDs and their method/universe tuples with the expected set. Record pending, completed, no-yield, blocked and failed assignments separately. Retry only unresolved work when useful; never describe a partial run as a completed all-method sweep. Interrupted runs resume from this ledger without silently repeating completed assignments. Distinguish settled assignments from a completed sweep: failed or blocked assignments leave the sweep incomplete even when every worker has stopped. A no-yield result counts as executed only when its artifact demonstrates that the operator was applied; an unsuitable method skipped without execution stays blocked. A completed run requires completed or evidenced no-yield results for every expected assignment in the current brief revision. Only the all-method axis may be described as an all-method sweep.
6. **Assess across methods.** Worker `retain` means a local lead, not a recommendation for the combined presentation. Use the form-before-story passes above to independently assess each proposed representative against the shared brief: intended promise, unwanted implications, plausible reading and explanation burden. Keep operator conformance separate from suitability: a correctly assembled name may be rejected without becoming a diagnostic. Park names whose intended reading needs unusual coaching or whose supported associations conflict with the brief; do not repair their story by hiding those facts. Record the conductor's judgment separately from worker assessments and user feedback. There is no quota of winners per method. An executed method can contribute zero recommended names without making coverage incomplete.
7. **Present and refine.** Group close sound variants, historical spellings and names carrying essentially the same promise as one presentation direction. Choose a representative for its fit, not because its method has not yet appeared. Preserve distinct candidate IDs, alternative lineages and all rejected/parked records in the pool. Show a small set of genuinely contrasting directions with a recommendation and concrete drawbacks; the full pool and coverage remain available on request. If no candidate is strong enough, say so and recommend one bounded change of source bank, sound palette or creative direction; do not manufacture a winner or restart every method. Compare representatives in identical contexts, then deepen the user's chosen directions. Before reporting the run complete, update the compact exploration log with coverage, the combined pool reference, conductor decisions, active/parked directions and next options. Preserve the existing shortlist and actual consent history. Never auto-save, delete favorites or export because workers finished. Shortlist consent and user control follow the existing contract.

A worker's output is evidence of one execution, not independent per-skill acceptance or consumer validation. Host scheduling and persistence need actual tool results; prose instructions alone do not prove enforcement.
