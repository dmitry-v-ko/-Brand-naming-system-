# Skill authoring and acceptance specification

An active skill lives at `skills/<id>/SKILL.md`; its stable ID equals the directory. Use `draft` until an independent reader can perform and review the supplied procedure. `ready` means operationally accepted, not commercially effective or legally cleared. `deprecated` routers and universe recipes do not count as active skills.

## Required executable substance

1. Metadata: ID, family, maturity, research requirement (`research-optional`, `research-recommended`, or `research-required for factual claims`), outputs and acceptance evidence.
2. A primary operator with closest-neighbor comparison, method-specific use/avoid decisions, required inputs, optional controls and reasonable inferred defaults.
3. Reproducible intermediate artifacts and transformations, diversification and pause rules. State exact retained/deleted/added units or supported semantic relationships. Batch sizes are private defaults, not demands on a user.
4. Method-specific selection criteria and a worked weak result → changed decision → repaired result; a valid but unsuitable output is as instructive as an invalid diagnostic. Initial menu previews must actually instantiate the offered operator.
5. A concrete retrieval route, provenance boundary and failed/unavailable-source alternative. Research-dependent skills need an actually inspected source/sense linked to the worked trace. Editorial invention remains legitimate when labeled; do not attribute the procedure to a source that supports only a broad category.
6. A complete synthetic trace: brief, contrasting previews, chosen branch, ledger/matrix, candidates, assessment, recovery, exact simulated feedback, favorites consent and resulting active/parked state. Never claim synthetic users are respondents.
7. Separate candidate form/evidence, source IDs or none, proposed pronunciation when useful, and exact ordered combinations with existing IDs.

## Review gates

Check the substance, not the presence of headings. Recompute maps manually; verify dictionary senses against actual access evidence; inspect both positive and negative implications; trace candidate IDs through state and export. Run a reader walkthrough across source failure, construction/sound refinement, delegated direction, switching, resuming and explicit-only export. Record shortcomings and repairs. Self-inspection is useful but is not an independent fresh-context trial.

Readiness decisions need a dated report naming skills checked, evidence paths and unresolved limits. Keep status draft where independent acceptance has not happened. Do not lower [fixed review weights](reviews/REVIEW_PROTOCOL.md) to accommodate implementation choices. A high review score must not hide a critical defect.
